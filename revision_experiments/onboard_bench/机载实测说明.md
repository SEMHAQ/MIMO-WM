# MIMO-WM 机载平台部署实测记录

本目录随补充材料提供机载部署实测的脚本、ONNX 模型、参考输入输出与原始结果 JSON，
使论文第 5.7 节与表 6 的数值可逐项复核。

## 1. 平台与软件

| 项 | 值 |
|---|---|
| 开发板 | 少林派 SLKY01 |
| 处理器 | 算能 BM1684，aarch64，8 核 |
| 推理框架 | ONNXRuntime 1.16.3，CPUExecutionProvider，纯 CPU，未启用板载专用加速器 |
| 系统 | Linux 4.9.38-bm1684-v10.5.0 aarch64 glibc 2.29 |
| 运行温度 | 45.0 至 45.5 摄氏度，测试期间未见降频 |

x86 参照机使用同一套 ONNX 文件与同一套输入，仅运行平台不同。

## 2. 测量口径

- **延迟**：单窗推理延迟的中位数，分别测 1 线程与 4 线程。重复次数随序列长度递减
  （$T{=}8$ 为 200 次，$T{=}16$ 为 150 次，$T{=}32$ 为 100 次，$T{=}64$ 为 50 次），
  前 15 次为预热不计入。单步延迟由整窗延迟中位数除以 $T$ 折算。
- **内存**：`VmHWM` 在进程内只增不减，一个进程内跑多个模型时它只反映"到目前为止的
  最大值"，无法归到单个模型。因此**每个序列长度单独起一个进程**运行，
  此时 `peak_rss_MB` 与该模型的 `rss_delta_MB` 才可归到该模型头上。
  `rss_delta_MB` 为加载该模型并完成首帧推理前后的进程常驻内存之差。
- **正确性**：与 `reference_io.npz` 中的参考输出逐元素比对最大绝对误差。
- **权重体积**：ONNX 文件本身的字节数。

## 3. 文件结构

```

│   ├── Transformer-Reg_T8 / _T32              ← 对照：常规规模（D=192, L=3）
│   ├── LSTM-WM_T8 / _T32                      ← 对照：循环基线
│   ├── GRU-WM_T8 / _T32                       ← 对照：循环基线
```

## 4. 复现命令

```bash
cd deploy_bench

# 锁性能模式，排除降频
sudo sh -c 'for p in /sys/devices/system/cpu/cpufreq/policy*; do echo performance > $p/scaling_governor; done'

# (1) 逐窗口单独进程测速：内存才可归到单个模型
for w in MIMO-WM_T8 MIMO-WM_T16 MIMO-WM_T32 MIMO-WM_T64 \
         Transformer-WM_T8 Transformer-Reg_T8 LSTM-WM_T8 GRU-WM_T8 TCN-WM_T8; do
    python3 bench_sbc.py $w
done

# (2) CEM-MPC 规划耗时
python3 bench_mpc_sbc.py
```

传入完整窗口名（如 `MIMO-WM_T8`）时只跑该窗口；传入模型名（如 `MIMO-WM`）时跑该
模型的全部窗口，此时 `peak_rss_MB` 是进程内累计峰值，不可单独归到某一个窗口。

## 5. 结果

### 5.1 MIMO-WM 的延迟与内存（论文表 6）

| $T$ | 1 线程延迟 (ms) | 4 线程延迟 (ms) | 单步延迟 (ms) | 常驻内存增量 (MB) | 进程常驻内存峰值 (MB) |
|---|---|---|---|---|---|
| 8 | 2.69 | 2.95 | 0.337 | 9.6 | 52.8 |
| 16 | 5.29 | 5.67 | 0.331 | 12.7 | 58.7 |
| 32 | 10.44 | 11.35 | 0.326 | 19.1 | 71.3 |
| 64 | 20.64 | 22.48 | 0.323 | 31.1 | 95.2 |

正确性：$T{=}16$、32、64 与参考输出的最大绝对误差为 0.0，$T{=}8$ 为 $2.4\times10^{-7}$。

进程常驻内存峰值中含约 38.6 MB 的 Python 与 ONNXRuntime 运行时本身开销，该值与模型
无关。内存增量随 $T$ 增大，源于部署所用的 ONNX 图为按步展开实现、其中转张量随 $T$
增加；权重体积本身与 $T$ 无关，$T{=}8$ 时 ONNX 文件为 0.60 MB。

### 5.2 同批测量的各模型对照（$T{=}8$，1 线程）

| 模型 | 单步延迟 (ms) | 常驻内存增量 (MB) | 权重 (MB) |
|---|---|---|---|
| GRU-WM | 0.116 | 7.5 | 0.77 |
| TCN-WM | 0.143 | 7.2 | 0.76 |
| LSTM-WM | 0.146 | 7.5 | 0.92 |
| Transformer-WM | 0.200 | 8.7 | 0.80 |
| MIMO-WM | 0.337 | 9.6 | 0.59 |
| Transformer-Reg | 0.717 | 15.3 | 2.54 |

**本表在论文正文与回复信中均未引用，正文也未据此作任何对比结论。** 在此完整列出，
是为了让补充材料自身可被复核——原始 JSON 已随本目录提供，读者可自行读取。

需如实说明 MIMO-WM 在此表中偏慢的原因：其部署 ONNX 由 `forward_window` 按步展开为
$T$ 个串行子图，而 LSTM、GRU、TCN 在 ONNXRuntime 中是单个融合算子、一次处理整窗。
这是导出方式的差异，不是架构计算量的差异。该展开也解释了单步延迟几乎不随 $T$ 变化
（0.337 至 0.323 ms），以及内存增量随 $T$ 增长。若实际部署改为按单步递推调用，
两者都可下降。论文第 5.6 节已说明 FLOPs 与实测延迟在小尺度下不成比例，第 5.7 节
已说明按步展开这一实现事实。

### 5.3 x86 参照（同一套 ONNX，ONNXRuntime CPU）

| 模型 | $T{=}8$ 中位延迟 (ms) | 权重 (MB) |
|---|---|---|
| TCN-WM | 0.136 | 0.76 |
| GRU-WM | 0.165 | 0.77 |
| LSTM-WM | 0.167 | 0.92 |
| Transformer-WM | 0.230 | 0.80 |
| MIMO-WM | 0.408 | 0.59 |
| Transformer-Reg | 0.645 | 2.54 |

x86 上的快慢排序与板上不同，主因同样是按步展开与融合算子的差别。论文第 5.7 节引用
的 x86 单窗延迟为 0.32、0.64、1.30 与 2.64 ms，依次对应 $T{=}8$、16、32 与 64，
与本表 $T{=}8$ 的 0.408 ms 为不同批次测量，量级一致。

### 5.4 机载 CEM-MPC 规划耗时

| 配置 | 单次规划 (s) | 频率 (Hz) |
|---|---|---|
| 候选 256、精英 32、5 轮、时域 10 | 5.82 | 0.17 |
| 候选 32、3 轮、时域 5 | 0.42 | 2.41 |

规划频率与候选规模近似成正比：论文中 7.99 Hz 的控制频率由 GPU 上并行评估 256 条
候选序列测得，在算力受限的机载端需按算力缩减候选规模，或借助板载专用加速器。

## 6. 注意事项

- **x86 与板上的快慢排序不可互相外推**，两者都受导出与算子融合方式影响。
- **如实记录，包括对本文模型不利的结果。** 数据不完整比数据不好更麻烦。
- 内存口径必须逐窗口单进程，否则 `peak_rss_MB` 无法归到单个模型。
